# Client API specification (v1)

JSON over HTTP(S). The request/response shapes are defined in Go in
`internal/api/types.go` (the source of truth); this document defines the
endpoints and their semantics. Every node serves the same API and a client may
talk to any node.

## 1. Conventions

* Bodies are `application/json` (a request body with any other `Content-Type`
  is `400 bad_request`; this also forces browsers to preflight cross-origin
  requests). Unknown fields and trailing data after the JSON value are
  `400 bad_request`. `[]byte` values are standard base64 with padding.
  A known path with the wrong method is `405` (code `bad_request`, `Allow`
  header set); an unknown `/v1/` path is `404 not_found`.
* IDs are 32 lowercase hex chars generated by the client. Usernames match
  `^[a-z0-9][a-z0-9._-]{0,31}$` (the server lower-cases and trims input first).
* Authenticated requests send `Authorization: Bearer <token>`.
* Every non-2xx response carries `api.ErrorBody`.
* **Idempotency:** every mutating request may carry an
  `Idempotency-Key: <32 hex chars>` header. Two requests with the same key
  from the same user are applied **once**; the second receives the first one's
  result. Clients always send one and reuse it when retrying after a network
  error, a timeout or `outcome_unknown`. (Without the header the server
  invents a key, so a blind client retry is then *not* de-duplicated.)
  Reusing a key for a *different* request (other path ids or body) is
  `400 bad_request` and changes nothing. Failed writes are remembered too, so
  a retry gets the same answer. Keys are remembered for the 4096 most recent
  writes cluster-wide. A retry whose own original request revoked the
  caller's token (password change, revoke-sessions) is still answered with the
  recorded result; for a password change or a registration the retry must
  carry the same (new) login key, and a replay never yields a token without it.
* **Consistency:** reads are linearizable by default: the node confirms via
  Raft (ReadIndex) that it is serving current data, which requires a majority
  of nodes to be reachable. `prelogin`, `login` and `sync` accept
  `?consistency=stale`, which serves from the node's local state with no
  quorum check (possibly out of date; `sync` then sets `"stale": true`).
  Clients use it only as a fallback when the linearizable call returns
  `unavailable`, so that a lone surviving server can still be read. Any other
  `consistency` value is `400 bad_request`. Stale serving is **bounded**: a
  node refuses stale reads (`503 unavailable`, message "stale read window has
  elapsed") once it has not known a Raft leader for longer than its stale
  read window (default 7 days; configurable, and a negative value disables
  stale reads). Otherwise a node cut off from the cluster would keep honouring
  a password or session revoked elsewhere indefinitely. The node samples
  whether it knows a leader about once a second; the window counts from the
  node's start if it has never seen one.
* **Writes** succeed only after a majority of nodes have durably stored them.
  A node that is not the leader forwards the write to the leader internally;
  the client does not need to know who the leader is.
* `503 unavailable` means nothing was changed (no leader/quorum).
  `503 outcome_unknown` means the write was submitted but not confirmed in
  time; retry with the same `Idempotency-Key`.
* Limits: request body 1 MiB (rekey: 32 MiB; the unauthenticated `prelogin`
  and `login`: 4 KiB; `register`: 32 KiB); item blob 64 KiB; `enc_meta`
  4 KiB; `enc_roster` 16 KiB; every box at least 41 bytes; wrapped key blob
  exactly 105 bytes; 32 users; 32 vaults per creator (including the personal
  vault); 10 000 items per vault. Exceeding a size limit is `413 too_large`;
  exceeding a count or quota is `422 limit_exceeded`, with a message naming
  the limit.
* **Storage quotas.** A vault's usage is `len(enc_meta) + len(enc_roster)`
  plus, per item, `len(blob) + 128` (the fixed per-item charge covers the
  item's metadata, so the replicated state, and with it a full snapshot,
  stays bounded whatever the item sizes). Quotas: **8 MiB per vault**,
  **16 MiB per user** (summed over the vaults the user *created*; writes by
  other members are charged to the creator) and **48 MiB for the household**.
  They keep a full snapshot far below the peer transport's 128 MiB message
  limit (a household at the quota snapshots to about 75 MiB), so a lagging or
  replaced node can always catch up, and they guarantee that any vault can be
  rekeyed within the 32 MiB rekey body limit (a vault at its quota needs
  about 11 MiB). They are checked when a write *adds* bytes (`put_item`,
  `rekey`, `create_vault`, `update_vault_meta`, `put_member` and the
  registration's personal vault); a write that does not grow usage (a delete,
  a same-size or smaller overwrite, a same-size rekey) is always accepted,
  even when a quota is already exceeded. Limits are enforced on writes only:
  a state that exceeds them (e.g. restored after a limit was lowered) is
  still accepted.
* **Registration bodies** are small in practice: the personal vault's roster
  lists one member (a few hundred bytes), so a registration that put every
  field at its individual maximum would exceed the 32 KiB register body
  limit (`413`).

## 2. Endpoints

### Public

| Method & path        | Body → Response                         | Notes |
|----------------------|------------------------------------------|-------|
| `GET /v1/health`     | → `HealthResponse`                       | Local view, never blocks on consensus. |
| `GET /v1/cluster`    | → `ClusterResponse`                      | From static config; lets clients learn the other nodes for failover. |
| `POST /v1/prelogin`  | `PreloginRequest` → `PreloginResponse`   | Unknown usernames get a deterministic fake salt and default parameters (§3.3) so usernames cannot be enumerated. |
| `POST /v1/register`  | `RegisterRequest` → `LoginResponse`      | §4 |
| `POST /v1/login`     | `LoginRequest` → `LoginResponse`         | `401 unauthorized` on unknown user, wrong key or disabled user (indistinguishable). Rate limited (§3.4). |

### Authenticated

| Method & path                               | Body → Response                              | Who |
|---------------------------------------------|-----------------------------------------------|-----|
| `GET /v1/sync[?since=N]`                    | → `SyncResponse`                              | any user |
| `POST /v1/account/password`                 | `ChangePasswordRequest` → `LoginResponse`     | any user |
| `POST /v1/account/revoke-sessions`          | → `LoginResponse`                             | any user |
| `POST /v1/vaults`                           | `CreateVaultRequest` → `MutationResponse`     | any user (becomes owner) |
| `PUT /v1/vaults/{vault}/meta`               | `UpdateVaultMetaRequest` → `MutationResponse` | owner |
| `DELETE /v1/vaults/{vault}`                 | → `MutationResponse`                          | owner; personal vaults cannot be deleted |
| `PUT /v1/vaults/{vault}/members/{user}`     | `PutMemberRequest` → `MutationResponse`       | owner |
| `DELETE /v1/vaults/{vault}/members/{user}`  | → `MutationResponse`                          | owner, or the member themself (leave) |
| `POST /v1/vaults/{vault}/rekey`             | `RekeyRequest` → `MutationResponse`           | owner |
| `PUT /v1/vaults/{vault}/items/{item}`       | `PutItemRequest` → `MutationResponse`         | owner, editor |
| `DELETE /v1/vaults/{vault}/items/{item}?base_version=N` | → `MutationResponse`              | owner, editor |
| `POST /v1/invites`                          | `CreateInviteRequest` → `CreateInviteResponse`| admin |
| `GET /v1/invites`                           | → `ListInvitesResponse`                       | admin |
| `DELETE /v1/invites/{invite_id}`            | → `MutationResponse`                          | admin |
| `PUT /v1/admin/users/{user}`                | `AdminUpdateUserRequest` → `MutationResponse` | admin |
| `GET /v1/admin/cluster`                     | → `AdminClusterResponse`                      | admin |
| `GET /v1/admin/backup`                      | → `ServerBackup`                              | admin |

A vault the caller is not a member of is indistinguishable from one that does
not exist (`404 not_found`). The one explicit exception: `POST /v1/vaults`
with an ID that is already taken answers `409 already_exists` to anyone. Vault
IDs are 128-bit client-generated random values, so this can only tell someone
who already knows the ID (a former member) that the vault still exists.
Malformed input is reported (`400`/`413`) before permissions are checked;
this reveals nothing about the state.

Notes on the vault endpoints (details in §5):

* `POST /v1/vaults`: `enc_roster` is required (the creator as sole owner).
  `MutationResponse.version` is the new `meta_version` (which is also the
  initial `roster_version`).
* `PUT .../members/{user}`: `enc_roster` and `base_roster_version` are
  required, for additions and role changes alike; `version` in the response
  is the new `roster_version`.
* `DELETE .../members/{user}`: unchanged; leaves the roster untouched and sets
  `rekey_recommended`. Owners normally remove members through the rekey.
* `POST .../rekey`: `enc_roster` is required; the optional `remove` list
  removes members atomically with the rekey.

`GET /v1/admin/cluster` must work exactly when the cluster is unhealthy, so it
does not wait for a read barrier: the session and admin flag are checked
against the node's local state (the response holds only operational
metadata).

`GET /v1/admin/backup` is linearizable. Its `state` contains **everything in
the replicated state except the cluster key**: all ciphertext (vault
metadata, rosters, items, wrapped vault keys), and also every user's password
verifier, KDF salt and parameters, wrapped account key and encrypted private
key, the membership graph (who shares which vault with whom, roles, who added
whom), usernames, invite hashes and the idempotency table. That is everything
needed to mount an offline guessing attack on every master password, so a
backup is **as sensitive as a server's disk** and must be stored like one.
Omitting the cluster key means a leaked backup cannot be used to forge
session tokens; a cluster seeded from a backup generates a new key, so every
user logs in again.

## 3. Authentication

### 3.1 Password verifier

The server never stores `login_key`. The node that handles a registration or
password change generates a random 16-byte salt and computes

```
verifier = Argon2id(login_key, salt, t = 2, m = 19456 KiB, p = 1, outLen = 32)
```

and only `{salt, t, m, p, verifier}` enters the Raft log and the replicated
state. Login recomputes it and compares in constant time. `login_key` must be
exactly 32 bytes. The state machine accepts only exactly these verifier
parameters (so no input can choose the memory cost of a login), and accepts
client KDF parameters (registration, password change) only within the
bounds clients enforce (crypto.md §2): `alg = "argon2id"`,
`16 <= len(salt) <= 64`, `65536 <= memory_kib <= 262144`, `3 <= time <= 8`,
`1 <= parallelism <= 16`, else `400 bad_request`. An account can thus never
be stored in a state its own clients would refuse. (These bounds are policy
for new writes; a restored state is only checked structurally.)
A node runs at most 4 Argon2 computations at once; a request that cannot get
a slot within a few seconds is answered `503 unavailable`.

### 3.2 Tokens

Tokens are stateless so that any node can verify them:

```
payload = base64url_nopad(JSON {"uid": <user id>, "ep": <token epoch>, "iat": <unix s>, "exp": <unix s>, "at": <unix s>})
token   = "v1." + payload + "." + base64url_nopad(HMAC-SHA256(clusterKey, "fpv/v1/token|" + payload))
```

`clusterKey` is 32 random bytes that live in the replicated state. It is
created exactly once: any node that sees an uninitialized state proposes an
`init` command carrying a fresh random key, and the first one applied wins.

A token is valid iff the MAC verifies, `exp` is in the future,
`now - at <= MaxSessionAge`, the user exists and is not disabled, and `ep`
equals the user's current **token epoch**.

`at` is the **auth time**: when the login key was last proven. Login,
registration and password change set it to now; `revoke-sessions` (which
issues a fresh token without a password) copies it from the presented token.
So a session, refreshed or not, ends `MaxSessionAge` (default 30 days) after
the password was last entered, and a stolen token cannot be kept alive
forever. A minted token's `exp` is `min(now + lifetime, at + MaxSessionAge)`.
Tokens without `at` are invalid. The epoch is bumped by password change, revoke-sessions and
disable, which instantly revokes all older tokens (enabling, granting or
revoking admin do not bump it). Default lifetime: 12 h. The epoch starts at
1. `LoginResponse.expires_at` is `exp` in milliseconds. A node that has not
yet learned the cluster key (it is still catching up) answers authenticated
requests with `503 unavailable`, not `401`, so clients keep their token and
fail over.

Every mutating command also carries the caller's `(uid, ep)`, and the state
machine re-checks them (and all permissions) when the command is applied, so
authorization is decided against the state the command actually executes on,
not a possibly stale local view.

### 3.3 Fake prelogin answers

For an unknown username: `salt = HMAC-SHA256(clusterKey, "fpv/v1/fake-salt|" + username)[:16]`
with the default KDF parameters (`t=3, m=65536, p=4`).

### 3.4 Rate limiting

Per node, in memory: failed logins are limited per username and per client
IP (token buckets; defaults 10 failures per 5 minutes per username, 30 per
5 minutes per IP). Exceeding it returns `429 rate_limited` with
`retry_after_ms`. Registration attempts are limited per IP the same way
(every attempt counts; default 10 per 5 minutes).

Details: a token is reserved from both buckets *before* the password check
and returned on success, so parallel guesses cannot all slip in before the
first failure is counted, and successful logins never consume the budget.
Unknown usernames count like known ones (otherwise the limiter would reveal
which exist). **Every** password check shares the per-username and per-IP
login budgets, not only `/v1/login`: the `current_login_key` of a password
change, and the login key a de-duplicated replay of a registration or
password change must prove (§1, Idempotency). A budget exhausted by one path
blocks all of them. IPv6 clients are keyed by their /64.

The client IP is the socket peer. A node may be configured with a trusted
proxy header (e.g. `X-Forwarded-For`) and a list of trusted proxy CIDRs
(default when the header is configured: loopback only, `127.0.0.0/8` and
`::1/128`). The header is believed only when the socket peer is a trusted
proxy; the client IP is then the right-most address in the header that is
not itself a trusted proxy (entries further left were written by the client
and are ignored). At most 10 000 keys are tracked per limiter; when full, new
keys are refused (fail closed) rather than exempted.

## 4. Registration, invites, admin

* **The first user** (state has no users) must present the node's configured
  **bootstrap token** as `invite_code`, and becomes an admin. The node checks
  the token (constant time); the state machine accepts a bootstrap
  registration only while there are zero users, so exactly one can win.
* Everyone else needs an **invite** created by an admin. An invite code is 20
  random bytes rendered as 32 base32 characters (RFC 4648 alphabet, no
  padding) in groups of four separated by `-`; input is accepted
  case-insensitively with or without the dashes. The **canonical code** is the
  32 upper-case base32 characters without dashes (non-ASCII input is
  rejected, not case-folded). The state stores only
  `SHA-256(canonical code)` (over its ASCII bytes); `invite_id` is the first
  16 hex chars of that hash. Invites are single use and expire (default 72 h,
  max 720 h; an invite is valid while `now < expires_at`). Expiry is
  judged against the timestamp the handling node put into the command, so all
  replicas decide identically.
* Because only the hash is stored, a code can never be shown twice. When
  `POST /v1/invites` carries an `Idempotency-Key`, the code is derived as
  `HMAC-SHA256(clusterKey, "fpv/v1/invite-code|" + caller_id + "|" + key)[:20]`
  so that a retry with the same key reproduces the same code; without a key
  it is random.
* At most 64 invites may be pending (unused, unexpired, unrevoked) at once
  (`422 limit_exceeded`). Creating an invite garbage-collects revoked and
  expired unused invites; used invites are kept. `GET /v1/invites` lists all
  non-revoked invites (including expired ones not yet collected), oldest
  first. `DELETE /v1/invites/{id}`: unknown or already revoked is
  `404 not_found`, an already used invite is `403 invalid_invite`.
* Registration atomically creates the user and their **personal vault**.
  Errors: `invalid_invite`, `already_exists` (username or any id taken),
  `limit_exceeded`.
* Admins can disable/enable users and grant/revoke admin. The last enabled
  admin cannot be disabled or demoted (`409 version_conflict` is wrong here:
  use `403 forbidden` with a clear message). Admins have **no** access to
  other people's vaults. `PUT /v1/admin/users/{user}` with neither field set
  is `400 bad_request`; setting values equal to the current ones succeeds
  without changing `rev`.
* Usernames are lower-cased in ASCII only. The vault limit (32) counts the
  vaults a user *created* (including their personal vault), so the total is
  bounded and nobody can push someone else over the limit.

## 5. Vault semantics

* `rev` is a counter in the replicated state, incremented by every command
  that changes anything. `GET /v1/sync?since=N` returns `{"rev": N,
  "unchanged": true}` (plus `served_by`/`stale`) when the state's rev is still
  `N`; any other `N` gets the full response.
* **Items** use optimistic concurrency. `base_version = 0` creates and
  requires that the item does not exist. Otherwise `base_version` must equal
  the item's current `version`. On success the item's new `version` is the new
  global `rev`, so versions are never reused, even if an item is deleted and
  re-created. A mismatch is `409 version_conflict` with `current_version`.
  `DELETE` requires `base_version >= 1` (`400` otherwise); deleting an item
  that does not exist is `409 version_conflict` with `current_version: 0`.
  Meta updates use `base_meta_version` the same way (`meta_version` is the
  global rev of the last metadata write; a conflict reports the current
  `meta_version` as `current_version`).
* `key_epoch` on item writes and on every `PUT .../members/{user}` (additions
  and role changes: the uploaded roster is sealed under the current key)
  must equal the vault's current epoch, else `409 key_epoch_mismatch` (the
  client must sync and re-encrypt/re-wrap with the current key).
* **Roster.** Every vault stores `enc_roster`, its member list sealed under
  the vault key (crypto.md §6.3), and `roster_version`, the global rev of the
  last roster write (the CAS token). Both are in every sync view of the
  vault. The server never interprets the roster; it only stores it, checks
  its size (a box, at most 16 KiB) and counts it toward the quotas. It is
  written by `create_vault` and registration (required), by every
  `put_member` (required, compare-and-swap) and by every rekey (required).
* **Members.** The creator of a vault is its owner. Owners may add members,
  change roles (including making more owners) and remove members. The last
  owner cannot be removed or demoted. Any member may remove themself, except
  the last owner. A **personal** vault never has members other than its owner.
* **`PUT /v1/vaults/{vault}/members/{user}`** adds a member (`wrapped_key`
  present) or changes an existing member's role (`wrapped_key` omitted), and
  in both cases replaces the roster with `enc_roster`. Checks, in order:
  1. stateless validation: ids, `role` in owner/editor/viewer, `enc_roster` a
     box of at most 16 KiB, and if present `wrapped_key` exactly 105 bytes
     with `sender_id` == caller (`400`; `413` when too large);
  2. the caller must be a member (`404 not_found`) and an owner
     (`403 forbidden`); the vault must not be personal (`403 forbidden`);
     the target must be a registered user (`404 not_found`);
  3. `key_epoch` must be the current epoch (`409 key_epoch_mismatch`);
  4. adding: `wrapped_key` is required (`400`); role change: a `wrapped_key`
     for an existing member is `409 already_exists` (keys only change
     through a rekey), and demoting the last owner is `403 forbidden`;
  5. `base_roster_version` must equal the current `roster_version`, else
     `409 version_conflict` with `current_version` = the current
     `roster_version`, and nothing changes (two owners cannot silently
     overwrite each other's roster);
  6. storage quotas (`422 limit_exceeded`).

  On success the member is added or the role changed, `enc_roster` replaced,
  and `roster_version` = the vault's `rev` = the new global rev (returned as
  `version`). Every successful call is a write and bumps `rev`, even when
  the role is unchanged (the roster was replaced).
* **`DELETE /v1/vaults/{vault}/members/{user}`** (an owner removing someone
  immediately, or a member leaving) removes the membership, leaves the roster
  untouched and sets `rekey_recommended`. Owners normally remove members
  through a rekey instead, which is atomic.
* **Rekey** (`POST /v1/vaults/{vault}/rekey`) atomically removes the members
  in `remove` (optional) and replaces the vault key. Checks, in order:
  1. stateless validation: `enc_meta` (≤ 4 KiB) and `enc_roster` (≤ 16 KiB)
     present, every wrapped key 105 bytes with `sender_id` == caller, item ids
     unique, item blobs within limits, and `remove` lists valid user ids, no
     duplicates and never the caller (`400`; `413` when too large);
  2. the caller must be a member (`404`) and an owner (`403`);
  3. `base_rev` must equal the vault's current `rev` and `new_key_epoch` must
     be the current epoch + 1 (`409 version_conflict`, `current_version` =
     the vault's `rev`);
  4. every id in `remove` must be a current member (`400 bad_request`);
  5. `wrapped_keys` must cover **exactly the remaining members** (current
     members minus `remove`) and `items` exactly the current items
     (`409 version_conflict`);
  6. storage quotas (`422 limit_exceeded`).

  On success: the removed memberships are deleted; `enc_meta`, `enc_roster`,
  every remaining member's wrapped key and every item blob are replaced;
  `key_epoch` is incremented; `meta_version`, `roster_version`, every item's
  `version` and the vault's `rev` all become the new global rev;
  `rekey_recommended` is cleared. A removed member no longer sees the vault
  in sync and gets `404` on it. The last-owner rule cannot be violated (the
  caller is an owner and cannot be in `remove`; the server asserts it
  anyway). A personal vault accepts a rekey only with an empty `remove` and a
  single wrapped key, the owner's.
* Deleting a vault deletes its items and memberships.

## 6. Node-to-node

Raft traffic uses a separate listener (`peer_listen`) with mutual TLS; it is
not part of this API. See DESIGN.md §3.

## 7. Web UI

Every node also serves the single-page web client at `/` (embedded in the
binary) with a strict Content-Security-Policy, and answers CORS preflights for
the origins of the other nodes' `public_url`s so that a page loaded from one
node can fail over to another. Allowed request headers: `Authorization`,
`Content-Type`, `Idempotency-Key`. Origins are matched exactly (scheme, host
and non-default port); no credentials mode. A preflight from any other
origin is `403 forbidden`.
