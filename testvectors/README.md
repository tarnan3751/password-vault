# Cross-language test vectors: `crypto-v1.json`

Normative spec: `docs/spec/crypto.md`. This file lets an independent
implementation (the TypeScript client) prove it agrees byte for byte with the Go
one. It is generated by `go run ./cmd/gen-vectors` and checked in; a Go test
fails if it drifts from the generator. **Do not edit it by hand.**

## Conventions

* **Every raw binary value is a lowercase hex string**, and the field name
  ends in `_hex`. No base64 appears except inside the backup `file` text and
  inside roster JSON (where the spec says base64).
* Fields without `_hex` are literal text: JSON strings (UTF-8), integers, or
  booleans. Passwords, usernames, IDs, AAD strings and JSON documents are text.
  Where exact Unicode matters, a `_hex` twin gives the UTF-8 bytes.
* Integers fit in a JS `number` (largest: `key_epoch` 4294967295).
* "random" inputs are fixed values written out in full; nothing in the file
  needs a random generator.
* Every case has `id` (unique) and `description`. Groups are independent.
* Every positive case must be reproduced **exactly**; every `*_negative`
  group, every `decoding_reject` case and every `valid: false` /
  `acceptable: false` case must be **rejected** (an error/exception, never a
  wrong value). For AEAD failures the specific reason is irrelevant.
* Plaintext JSON texts (`plaintext_json`, `canonical_json`, `expected_json`)
  are compared as **bytes/strings, never re-serialised with your JSON library**:
  JSON text is not canonical across languages.

Names below: `hex(x)` = lowercase hex; `utf8(s)` = UTF-8 bytes; `seal`, `open`,
`sealWithNonce` as in spec section 3; `HKDF(ikm, salt, info, L)` is
HKDF-SHA-256 with `info` as UTF-8 text; `epoch` is a decimal integer in AAD
strings; `X25519` rejects an all-zero result (spec section 6).

## Published primitive vectors (library wiring)

Each has `source` naming the document the numbers come from.

* `argon2id_published`: `password_hex`, `salt_hex`, `time`, `memory_kib`,
  `parallelism`, `out_len`, `expected_hex`. Check `argon2id(password, salt, t,
  m, p, outLen) == expected`. Source: phc-winner-argon2 `src/test.c` (Argon2id
  v1.3, password `"password"`, salt `"somesalt"`). The RFC 9106 vector needs a
  secret key and associated data and is not used. One case uses 256 MiB; skip it
  in memory-constrained browser runs if you must.
* `hkdf_sha256_published`: `ikm_hex`, `salt_hex`, `info_hex` (salt/info may be
  empty), `length`, `prk_hex`, `okm_hex`. RFC 5869 A.1 and A.3. Check extract
  gives `prk` and `HKDF` gives `okm`. Empty salt = 32 zero bytes.
* `x25519_published`: `scalar_hex`, `u_hex`, `expected_hex`. RFC 7748 5.2/6.1.
  Check `X25519(scalar, u) == expected`.
* `xchacha20poly1305_published`: `key_hex`, `nonce_hex`, `plaintext_hex`,
  `aad_hex`, `ciphertext_hex`, `tag_hex`. draft-irtf-cfrg-xchacha A.3.1. Bare
  AEAD (no `0x01 || nonce` framing): encrypt gives `ciphertext || tag`; decrypt
  inverts it.

## Our constructions

### `master_keys` (spec sections 1, 2)
Fields: `username` (already normalized), `password`, `password_hex`,
`normalized_password_hex`, `salt_hex`, `argon_salt_hex`, `time`, `memory_kib`,
`parallelism`, `below_production_minimum`, `master_key_hex`, `enc_key_hex`,
`login_key_hex`. Check:
1. `utf8(NFKC(password)) == normalized_password_hex` (no trimming).
2. `argonSalt = SHA-256(utf8("fpv/v1/kdf-salt|" + username + "|") || salt) ==
   argon_salt_hex`.
3. `MK = argon2id(normalized, argonSalt, t, m, p, 32) == master_key_hex`.
4. `HKDF(MK, empty, "fpv/v1/enc-key", 32) == enc_key_hex`; likewise
   `"fpv/v1/login-key"` and `login_key_hex`.
5. If `below_production_minimum`, the validating `deriveMasterKeys` must refuse
   the parameters while the test-vector-only variant derives the keys above;
   otherwise the validating function must derive them.
`mk-other-username-cheap` differs from `mk-ascii-cheap` only in the username
(every key differs). The two `mk-nfkc-*` cases are one password in two Unicode
spellings (`password` differs, normalized bytes and keys are equal).
`mk-production-defaults` (t=3, 64 MiB, p=4) and `mk-production-max-bounds-p16`
are the only production-cost cases.

### `kdf_params_validation` (spec section 2)
Fields: `alg`, `salt_hex`, `time`, `memory_kib`, `parallelism`, `valid`.
`validateKdfParams` accepts iff `valid`. Rule: `alg == "argon2id"`,
`16 <= len(salt) <= 64`, `65536 <= memory_kib <= 262144`, `3 <= time <= 8`,
`1 <= parallelism <= 16`.

### `kdf_not_weaker` (spec section 2)
Fields: `cached_time`, `cached_memory_kib`, `offered_time`,
`offered_memory_kib`, `acceptable`. A device with cached parameters refuses
offered ones with a smaller `memory_kib` **or** a smaller `time` (parallelism and
salt are not compared). `acceptable == !(offered_m < cached_m || offered_t <
cached_t)`.

### `box` / `box_negative` (spec section 3)
`box`: `key_hex`, `nonce_hex`, `plaintext_hex`, `aad_hex`, `box_hex`; check
`sealWithNonce(key, nonce, plaintext, aad) == box` and `open` inverts it.
`box_negative`: `key_hex`, `aad_hex`, `box_hex` (may be empty); `open` fails.

### `key_pairs` (spec section 4)
`private_key_hex`, `public_key_hex`: `X25519(private, basepoint) == public`
(private used as-is).

### `fingerprints` (spec section 6.2)
Fields: `user_id`, `username`, `public_key_hex`, `fingerprint`. Check
`h = SHA-256(utf8("fpv/v1/fingerprint|" + user_id + "|" + username + "|") ||
publicKey)`; the first **16** bytes as 32 lowercase hex characters in **eight**
groups of four separated by `-` equals `fingerprint`. `fp-same-key-*` cases give
the same key to different usernames / user IDs and therefore different
fingerprints; `fp-same-identity-other-key` changes only the key.

### `vault_key_wrap` / `vault_key_wrap_negative` (spec section 6)
Positive fields: `sender_private_hex`, `sender_public_hex`, `sender_id`,
`recipient_private_hex`, `recipient_public_hex`, `recipient_id`, `vault_id`,
`key_epoch`, `vault_key_hex`, `ephemeral_private_hex`, `ephemeral_public_hex`,
`nonce_hex`, `aad` (text), `wrap_hex`. Check: deterministic wrap (with the given
ephemeral secret and nonce) `== wrap_hex` (105 bytes); `unwrap(wrap, ctx,
recipientPrivate, senderPublic) == vault_key`. `ctx = {vault_id, key_epoch,
sender_id, recipient_id}`.
Negative fields: `base_case`, `recipient_private_hex`, `sender_public_hex`,
`sender_id`, `recipient_id`, `vault_id`, `key_epoch`, `wrap_hex` (may be empty).
These are exactly the arguments of `unwrap`; it must fail (wrong sender key,
wrong ids/epoch, swapped ids, low-order ephemeral keys, all-zero sender key,
flipped bits, version 2, 104/106-byte and empty input).

### `padding` (spec section 5)
`input_hex`, `n`, `padded_hex`: `pad(input, n) == padded`. Empty input becomes
`n` spaces; non-empty multiples of `n` are unchanged.

### `vault_meta` / `vault_meta_negative` (spec sections 5, 5.1)
Positive: `vault_id`, `key_epoch`, `key_hex`, `nonce_hex`, `plaintext_json`,
`aad`, `padded_length`, `blob_hex`. Check `aad == "fpv/v1/vault-meta|" +
vault_id + "|" + key_epoch`; `sealWithNonce(key, nonce, pad(utf8(plaintext_json),
64), utf8(aad)) == blob`; open + decode (rules below) gives the document, whose
canonical re-encoding equals `plaintext_json`.
Negative: `key_hex`, `vault_id`, `key_epoch`, `blob_hex`: opening with
`"fpv/v1/vault-meta|" + vault_id + "|" + key_epoch` fails (wrong epoch - right
key, vault and blob -, older epoch, wrong vault, wrong key).

### `items` / `items_negative` (spec section 5.2)
Positive: `vault_id`, `item_id`, `key_epoch`, `key_hex`, `nonce_hex`,
`plaintext_json`, `aad`, `padded_length`, `blob_hex`. `aad == "fpv/v1/item|" +
vault_id + "|" + item_id + "|" + key_epoch`; `sealWithNonce(key, nonce,
pad(utf8(plaintext_json), 256), utf8(aad)) == blob`; open + decode +
canonical encode reproduces `plaintext_json`. `item-login-full` carries an
unknown member `x_future` whose raw text contains odd spacing: it must survive a
decode/encode round trip untouched.
Negative: `key_hex`, `vault_id`, `item_id`, `key_epoch`, `blob_hex`; opening
fails (other item, other vault, swapped ids, other key, epoch 4 and epoch 1
instead of 3).

### `rosters` / `rosters_negative` (spec sections 5, 6.3)
Positive: `vault_id`, `key_epoch`, `key_hex`, `nonce_hex`, `plaintext_json`,
`aad`, `blob_hex`. `aad == "fpv/v1/roster|" + vault_id + "|" + key_epoch`;
`encRoster = sealWithNonce(key, nonce, utf8(plaintext_json), aad)` with **no
padding**; open + decode + canonical encode reproduces `plaintext_json`.
Roster canonical encoding: `{"v":1,"members":[` + members joined by `,` + `]}`,
each member `{"id":"<id>","pk":"<standard padded base64 of 32 bytes>","role":"<role>"}`,
no whitespace. Members are sorted by `id` (plain string comparison of the
lowercase hex; not by name).
Negative: `key_hex`, `vault_id`, `key_epoch`, `blob_hex`: the client's
`decryptRoster` must fail. The first three are AEAD failures (wrong vault,
epoch, key). The rest are authentically sealed documents that violate an
invariant: unsorted, duplicate id, no owner, empty list, bad role (also
`"Owner"`), 31- or 33-byte key, unpadded base64, `v` = 2 or 1.0, malformed
ids, missing role, duplicated `members`, a `null` entry, trailing garbage, not
JSON, invalid UTF-8. Invariants: `v == 1`; ids valid (32 lowercase hex), sorted
strictly ascending (hence unique); `pk` decodes (standard base64, padded, no
whitespace, canonical) to exactly 32 bytes; `role` in {owner, editor, viewer}
(case-sensitive); at least one owner. Unknown members (top level or in entries)
are ignored.

## Decoding rules (spec section 5.3)

Applies to the **plaintext** of meta, item and roster boxes (after `open`, with
any padding still in place). A conforming decoder:

1. Requires valid UTF-8 (no replacement characters, no overlong forms, no
   encoded surrogates).
2. Requires exactly one JSON object, with only JSON whitespace (space, TAB,
   LF, CR) before and after it. Anything else after the object is an error.
3. Is strict RFC 8259: no comments, trailing commas, single quotes, NaN, raw
   control characters in strings, leading zeros. A `\u` escape that denotes a
   **lone surrogate** is an error anywhere (names and values, known or unknown
   members). A valid surrogate pair decodes to one character.
4. Matches member names **exactly**, after decoding escapes (`"name"` is
   `name`). `"Name"` is an unknown member.
5. Rejects a document in which a known name appears twice (at the top level,
   inside a `fields[]` entry, inside a `password_history[]` entry, inside a
   roster entry). Duplicates of unknown names are allowed and all are kept.
6. Requires known members to have exactly their type; `null` is never accepted
   in place of a known member nor as an element of `urls`, `tags`, `fields`,
   `password_history` or `members`. Unknown members may hold any valid JSON
   value, `null` included.
7. Integers (`v`, `created_at`, `updated_at`, `changed_at`) match
   `0|[1-9][0-9]*` and are <= 9007199254740991. `1.0`, `1e3`, `-0`, `-1`, `01`
   are all errors. Anything beyond 2^53-1 is an error even though it is valid
   JSON.
8. Requires `v == 1`; item `type` in {`login`, `note`}; `name` present (empty
   allowed) for items and metadata. Required members of a roster entry:
   `id`, `pk`, `role`. Other known item members are optional (absent = empty).
   Inside `fields[]` entries: `name`, `value` strings, `hidden` boolean, all
   optional. Inside `password_history[]` entries: `password` string,
   `changed_at` integer, optional.
9. Unknown members inside `fields[]` and `password_history[]` entries are
   ignored and dropped on re-encode. Unknown **top-level** members of an item
   or of vault metadata are kept, as raw text, in order (see below).
10. Nesting depth inside unknown members is unlimited (do not recurse
    unboundedly).

### `decoding_accept`
Fields: `kind` (`item` | `meta` | `roster`), `plaintext_hex`, `canonical_json`.
Check: decoding `plaintext_hex` succeeds, and the **canonical encoding** of the
decoded value equals `canonical_json` exactly. The canonical form is a fixed
point (decoding it and re-encoding gives it back). The expected values prove
which of two similar members a decoder picked (`dec-item-wrong-case-top` must
keep `name == "lower"` and carry `"Name":"UPPER"` as an unknown member).

### `decoding_reject`
Fields: `kind`, `plaintext_hex`. Check: decoding fails. Covers `"hidden":
null`, `"v": 1.0`, `"created_at": 1.5` and `1e3`, integers above 2^53-1,
duplicated known members (top level, inside a field entry, via escapes), wrong
case only (`"Name"` alone means missing name), null array elements, invalid
UTF-8 byte sequences, lone surrogate escapes, trailing garbage (`x`, a second
object, NUL, form feed) versus trailing spaces (accepted, in `decoding_accept`),
missing `name`/`v`/`type`, unknown `type`, top-level non-objects, metadata
without `name`, bad rosters.

### Canonical encoding (what your client writes after an edit)
Compact JSON, no whitespace between tokens.

* **Item**, member order: `v`, `type`, `name`, `username`, `password`, `urls`,
  `notes`, `totp`, `fields`, `tags` (each of `username`, `password`, `notes`,
  `totp` omitted when the empty string; `urls`, `fields`, `tags` omitted when
  empty), then `created_at` and `updated_at` **always** (absent decodes as 0
  and is written as 0), then `password_history` (omitted when empty), then the
  **unknown top-level members, in the order they appeared in the source
  document**, each as its raw key text, `:`, and its raw value text.
  `fields` entry: `{"name":..,"value":..}` plus `,"hidden":true` only when true;
  `password_history` entry: `{"password":..,"changed_at":..}`.
* **Vault metadata**: `{"v":1,"name":<name>` + unknown members as above + `}`.
* **Raw key / value text** is the exact substring of the source plaintext: the
  key including its quotes and escapes as written (`"xA"` stays as written),
  the value from its first to its last character (interior whitespace such as
  `{"a" : [1,  2]}` and numbers such as `12345678901234567890`, `1.0`, `-0`
  are untouched); whitespace around the value or around `:` and `,` is dropped.
  Duplicate unknown members are all kept.
* **Strings** (known members): `"` and `\` are escaped as `\"` and `\\`; the C0
  controls are escaped as `\b \t \n \f \r` where those short forms exist and
  `\u00xx` (**lowercase** hex) otherwise; every other character is written
  literally in UTF-8 - including `/`, `<`, `>`, `&`, U+007F, U+2028, U+2029 and
  all non-ASCII. (`JSON.stringify` behaves the same for strings without lone
  surrogates, which cannot occur here.)
* **Integers**: plain decimal.
* **Roster**: see `rosters`.

### `edit_preserve`
Fields: `kind` (`item` | `meta`), `plaintext_hex`, `new_name`, `expected_json`.
Check: decode `plaintext_hex`, set `name = new_name`, canonical-encode: the
result equals `expected_json` byte for byte. This pins "unknown top-level
members survive an edit byte for byte" and the order rule above (known members
first in canonical order, unknown ones in source order after them), including
wrong-case twins (`"Name"`), duplicates, an escaped key, and values
`12345678901234567890`, `1.0`, `-0` and nested objects with odd spacing. Note
that the editing code does **not** touch `updated_at`; `EditItem` bookkeeping is
separate.

## Rekey and trust-store primitives

### `reencrypt` (spec sections 5.3, 6.6)
Fields: `kind` (`item` | `meta`), `vault_id`, `item_id` (empty for meta),
`old_key_hex`, `new_key_hex`, `old_epoch`, `new_epoch`, `nonce_hex`,
`input_blob_hex`, `opened`, `output_blob_hex`. Check: try `open(old_key,
input, aad(old_epoch))` where aad is the item or meta AAD. If it opens:
`opened == true` and the output is `sealWithNonce(new_key, nonce, <the raw
plaintext bytes, padding included, nothing parsed or trimmed>,
aad(new_epoch))`. If it does not open (wrong key, wrong epoch, too short):
`opened == false` and the output **is the input blob, unchanged**. Raw means a
plaintext that is not even JSON (or is empty) is still re-encrypted.

### `vault_key_commitments` (spec section 6.2)
`vault_key_hex`, `vault_id`, `key_epoch`, `commitment_hex`:
`SHA-256(utf8("fpv/v1/vault-key-commit|" + vault_id + "|" + key_epoch + "|") ||
VK)` as lowercase hex (64 characters).

### `local_trust` / `local_trust_negative` (spec section 6.2)
Positive: `account_key_hex`, `user_id`, `trust_key_hex`, `nonce_hex`,
`plaintext_hex`, `aad`, `blob_hex`. `trust_key = HKDF(accountKey, empty,
"fpv/v1/local-trust-key", 32)`; `aad == "fpv/v1/local-trust|" + user_id`;
`blob = sealWithNonce(trust_key, nonce, plaintext, aad)`; open inverts it. The
plaintext is the client's business (arbitrary bytes here).
Negative: `account_key_hex`, `user_id`, `blob_hex`: open fails (other user, other
account key, flipped bit, truncated, empty, sealed with the account key itself).

## Master-password policy

`password_policy_common` (root array, 694 strings, sorted by byte order) is the
embedded list of common passwords to copy into the TypeScript client verbatim.

`password_policy` cases: `password`, `username`, `expect` (`"ok"` or a code),
`hint` (bool). It is a **floor, not a strength meter**. Procedure (the first
rule that fires decides; `pw = NFKC(password)` as code points):
1. `too_short`: fewer than 12 code points in `pw`.
2. `contains_username`: with `u` = username trimmed of ASCII whitespace and
   ASCII-lower-cased (only `A-Z` mapped), `low` = `pw` ASCII-lower-cased: `u`
   non-empty and (`low == u` or (`len(u) >= 3` and `low` contains `u`)).
3. `repeated`: `pw` consists of one code point repeated, or of a block of
   1 to 4 code points repeated to fill it exactly (period `p` in 1..4,
   `len % p == 0`, `pw[i] == pw[i-p]`).
4. `sequence`: every consecutive pair of code points differs by +1, or every
   pair by -1.
5. `common`: `low` is in `password_policy_common`.
`hint == true` means the passphrase nudge is shown: `pw` split on U+0020 has
fewer than four non-empty words. Accepted passwords can still have a hint.

## Accounts and backups

### `accounts` (spec section 4): full scenario
Fields: `user_id`, `username`, `password`, `kdf` {`salt_hex`, `time`,
`memory_kib`, `parallelism`} (the smallest accepted parameters, validated),
fixed inputs `account_key_hex`, `private_key_hex`,
`nonce_wrapped_account_key_hex`, `nonce_enc_private_key_hex`, expected outputs
`enc_key_hex`, `login_key_hex`, `public_key_hex`, `wrapped_account_key_hex`,
`enc_private_key_hex`, and `password_change` {`new_password`, `new_kdf`,
`new_nonce_hex`, `new_enc_key_hex`, `new_login_key_hex`,
`new_wrapped_account_key_hex`}. Check, in order:
1. derive master keys from `username` + `password` + `kdf` (NFKC, bound salt):
   equal `enc_key`, `login_key`.
2. `public_key = X25519(private_key, basepoint)`; `wrapped_account_key =
   sealWithNonce(encKey, nonce_wrapped, account_key, utf8("fpv/v1/account-key|"
   + user_id))`; `enc_private_key = sealWithNonce(accountKey, nonce_enc_priv,
   private_key, utf8("fpv/v1/private-key|" + user_id))`.
3. `unlock` returns `account_key` and `private_key`.
4. Password change (same username, new salt): the new keys equal the expected
   ones; `sealWithNonce(newEncKey, new_nonce, account_key, aad as in 2) ==
   new_wrapped_account_key`; unlocking with the new encKey, the new wrapped key
   and the original `enc_private_key` succeeds.

### `accounts_negative`
Fields: `user_id`, `username`, `password`, `kdf`, `public_key_hex`,
`wrapped_account_key_hex`, `enc_private_key_hex`, `expect_error`. Derive encKey
from `username` + `password` + `kdf`, then `unlock(user_id, ...)` fails with
`"decrypt"` (an AEAD open fails: wrong password, **wrong username**, wrong user
ID, swapped or truncated blobs) or `"public_key_mismatch"` (both opens succeed
but `X25519(privateKey, basepoint)` differs from `public_key`).

### `backups` (spec section 7)
Fields: `passphrase`, `alternate_passphrases`, `kdf`, `created_at`, `nonce_hex`,
`backup_key_hex`, `payload_json` (exact plaintext), `payload` (same document as
an object), `file` (the complete file as one string). The backup KDF uses the
**raw salt** (no username) and the same bounds as section 2. Check:
1. parse the envelope (`format == "fpv-backup"`, `version == 1`), validate
   `kdf` (bounds of `kdf_params_validation`), `BK = argon2id(NFKC(passphrase),
   salt, ...)`, `backupKey = HKDF(BK, empty, "fpv/v1/backup-key", 32)` (equals
   `backup_key_hex`), `open(backupKey, base64(blob), utf8("fpv/v1/backup"))`
   equals `utf8(payload_json)` byte for byte; its JSON parse equals `payload`.
   Items inside the payload follow the item decoding rules. Also decode with each
   alternate passphrase.
2. Optionally re-encode with `created_at` and `nonce_hex` and compare the
   decoded `blob` bytes. Do not compare the envelope text itself.

### `backups_negative`
Fields: `passphrase`, `file`, `expect_error`: decoding fails with
`not_backup` (not JSON, wrong shape, `format != "fpv-backup"`),
`unsupported_version` (file `version != 1`, or authenticated payload `v != 1`),
`weak_kdf` (parameters outside the bounds, salt not 16..64 bytes, or `alg`
wrong; **refused before running Argon2**, one case asks for 2 GiB) or `decrypt`
(wrong passphrase, tampered or truncated blob, wrong salt, wrong AAD).

## Regenerating

`go run ./cmd/gen-vectors`. `go test ./internal/vaultcrypto/... ./internal/backup/`
verifies every case through the public Go API and that the checked-in file equals
the generator's output.
